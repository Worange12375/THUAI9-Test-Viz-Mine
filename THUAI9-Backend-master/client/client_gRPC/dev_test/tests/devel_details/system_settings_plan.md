# 系统设置（System Settings）初步设计规划

目标：在测试端 UI 中提供一个“系统设置”窗口，用于承载后端暂未完善或不便修改的功能（通过运行时注入/测试端逻辑实现），并形成可持续扩展的入口。

## 1. 窗口定位

- 入口：主界面右侧按钮区「系统设置」
- 形式：`Toplevel` 弹窗，布局风格与「属性设置」一致
- 结构：左侧导航（一级页面）+ 右侧内容区（当前页面内容）
- 生效范围：默认仅测试端本局生效（不写回后端文件、不影响正式服务端）

## 2. 一级导航（固定顺序）

1) 综合设置
2) 玩法设计
3) 使用教程
4) 开发信息

> 后续如需扩展，优先在“玩法设计/开发信息”内部做二级导航，避免一级栏目过多。

## 3. 页面职责与预期内容

### 3.1 综合设置（General）

面向“可用性/显示/调试”类设置。

可能包含：
- 右下信息展示区的信息展示，现在已经实现信息的不同类别与重要程度，未来按此可以设计一个按需关闭部分类别的开关，优化信息显示。
- 目前的对局节奏适中，未来考虑是否要加入“加速节奏”的选项（例如缩短操作确认部分），以便快速测试。
- 目前系统有充分的异常情况的文字提示与弹窗提示，可以设置关闭弹窗
- 对于一些辅助显示（例如待选目标等），设计其开关和颜色

### 3.2 玩法设计（Design）

面向“玩法规则/行动规则/技能扩展”的入口，强调“配置 → 影响真实结算”。

可能包含：
- 全局规则（例如濒死等玩法）
- 行动规则编辑（攻击/法术/移动等参数面板的全局默认值、运算公式、天赋阶梯调整）
- 扩展点：职业/法术池/天赋/公式系统（例如各职业可用的法术池）
- 扩展点：设计新的攻击、法术等

实现策略建议：
- 仅在测试端设计，如果后端有，则做覆盖（即不更改后端，相关函数不用来自后端的数据实现，而是用来自测试端的实现）
- 未来设计一个保存机制，允许一键配置

边界：
- 不修改 `client_gRPC/env.py` 等后端源文件

### 3.3 使用教程（Tutorial）

面向用户使用与操作说明，内容会很长。

推荐方案：
- 教程内容放到独立文档（`.txt`等格式）
- UI 读取文件内容并展示在可滚动 `Text` 中

原因：
- 减少 `main_ui.py` 体积与维护成本
- 文案改动不需要动代码逻辑

### 3.4 开发信息（Dev Info）

- 上部分页面展示我们比赛开发者的信息（信息较少，直接编写）
- 下部分做隐藏，只有dev及更高权限者才可看到:
主要是面向开发者的状态快照与调试信息。主要是`devel_details`


## 4. 与权限系统的关系（预留）

- 后续可能引入 3 层权限：基础 / 开发 / 最高
- 系统设置页面内的某些“危险”项（例如强制改规则、注入结算逻辑）应受权限控制
- 当前不实现鉴权，只在代码结构上避免把“敏感设置”散落在各处：
  - 推荐：所有受限项集中在系统设置模块内部
  - 通过统一的 `permission_level` 查询决定是否显示/可编辑

目前的设计是，“系统设置”中，未来会加权限的是
1.整个玩法设计
2.开发信息中的下半部分（快照等）
3.综合设置中可能的某些选项
