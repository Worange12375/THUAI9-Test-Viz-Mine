# 权限系统（Permission System）初步设计（预留，不实现）

目标：为测试端 UI 的“系统设置/玩法设计/开发信息”等能力预留权限控制点，避免后续接入时需要大规模重构。

> 当前阶段：只写设计与接口约束，不实现鉴权流程。

## 1. 权限等级定义

三层权限：

1) 基础权限（basic）
- 面向普通使用者
- 可查看教程、查看一般信息、调整“无风险”的 UI 显示项

2) 开发权限（dev）
- 面向调试与玩法迭代
- 可访问更详细日志/状态，允许启用“本局注入”的规则开关

3) 最高权限（root）
- 面向核心维护者
- 可访问高风险设置：修改结算关键规则、强制覆盖资源/距离限制、批量注入或调试接口

## 2. 权限控制的对象

### 2.1 可见性（Visibility）
- 某些页面/模块仅在 dev/root 显示
- 某些按钮/选项仅在 dev/root 显示

### 2.2 可编辑性（Editability）
- basic 只能读，dev 可改一部分，root 可改全部
- 对高风险设置采用“只读展示 + root 解锁编辑”的模式

### 2.3 可执行性（Execution）
- 即便 UI 可见，执行时也应二次校验权限（防止未来被脚本/回调误调用）

## 3. 建议的代码结构（避免散落）

推荐在 UI 侧统一封装权限查询与校验：

- 单一状态：`self.permission_level`（字符串或枚举）
- 单一入口：
  - `self._get_permission_level() -> str`
  - `self._has_permission(required: str) -> bool`
  - `self._require_permission(required: str) -> bool`（不满足则弹提示并返回 False）

约束：
- 所有“敏感设置”的回调函数，必须在函数开头调用 `_require_permission`。
- 页面构建时根据 `_has_permission` 决定是否渲染对应控件。

## 4. 权限存储与认证入口（未来可能方案）

### 4.1 最简单（本地明文，适合测试端）
- 在系统设置里输入一个“开发口令/令牌”
- 验证通过后把 level 写入内存变量（仅本次运行）

优点：实现简单；风险可接受（测试端）。
缺点：不适用于生产。

### 4.2 读取本地配置文件（推荐用于团队协作）
- `dev_test/data/permission.json` 存放 level 与过期时间
- 支持忽略提交（gitignore）

优点：可复用；便于多人。
缺点：仍是本地信任模型。

### 4.3 与后端认证联动（更正式）
- 通过 gRPC/HTTP 拉取角色信息
- UI 仅作展示与控制

优点：一致性好。
缺点：需要后端支持，不符合当前“测试端补位”的节奏。

## 5. 哪些功能建议受限（初步）

- basic：
  - 查看教程
  - 查看当前局基础信息
  - 打开系统设置但只能访问“综合设置/使用教程”中的无风险项

- dev：
  - 开启详细日志
  - 查看/导出 snapshot
  - 启用“本局规则注入”（但不允许覆盖破坏性规则）

- root：
  - 修改结算关键路径相关注入（攻击/法术/死亡判定/胜负判定）
  - 覆盖资源/距离/冷却限制（仅用于调试）

## 6. 落地建议（当前阶段）

- 先在系统设置代码中预留 `permission_level` 的字段与检查函数（但默认全部 basic 且不弹任何鉴权输入）。
- 敏感项的回调签名与调用路径尽量集中在系统设置模块，避免未来改动面过大。
